# Bot 创建失败与生命周期修复

## 现场证据（2026-11-16）

- 本次只处理 Bot 创建故障，不合入暂停中的资源区样式修改。
- 实际运行插件与团队面板工作树 `7ec7fe9` 的 `bots.js` SHA256 相同。
- 真实会话第一步已成功调用 `bot_directory` 和 `team_profile_get`，工具安装正常。
- 首次 `bot_create` 距 turn/start 约 7.1 秒，模型已选择名称与职责；工具在 4ms 后返回 `cannot get property "agentPresets" without inject`。
- 第二次调用发生同样错误。后续转入源码/命令探索，总计 33 次工具调用，整轮约 309 秒。
- 所以本次确证根因不是模型没拿到工具，不是浏览器渲染，也不是登记文件 IO 缓慢，而是 Cordis 依赖声明缺失。
- 旧测试直接用普通 JS 对象当 ctx，没有覆盖真实 Cordis service getter 的注入约束。

## 实现

1. `installBots` 显式注入 `agentPresets`；`bot_create` 从该服务读取当前 Session 的实际 preset，不改模型或权限。
2. 同一已绑定 Session 使用相同 name/kind/purpose/cwd/preset 再次创建时，返回原 Bot，不重复落盘、不重复通知、不递增 revision。
3. 不同参数不会悄悄改已有 Bot；归档对象不会被重试复活。名字、职责和归档变更仍走原来的 CAS update。
4. 已取消的工具调用在读取 preset/写盘前结束。
5. 工具描述与系统约定明确：这是已有产品操作，直接调用；保存成功即结束身份创建；失败核对目录一次后报告。不把缺少的外部账号、工具配置或团队成员声称为已就绪。
6. `/naumi/bots` 响应增加 `X-Naumi-Bots-Contract: 2`，用于确认服务确实加载本轮代码。目录 schema version 仍为 1，不迁移数据。

## 验证设计

- 使用真正的 Cordis Context，host-services 与 enterprise 插件放在 sibling fibers，确保未注入的服务访问会真实报错；不是绕过权限检查的裸对象测试。
- Host adapters 使用临时文件与隔离 Agent，不调用模型、不创建用户目录 Bot。
- 覆盖已存在/晚创建 Agent 的工具安装、preset 为 null、并发重复调用、持久化后重启、输入冲突、归档保护、写盘失败恢复、预先取消和模块卸载。
- 执行 Bot / Team / enterprise 模块测试；单独采样 25 次工具创建耗时。该耗时仅含本地生命周期操作，不等于线上模型端到端生成耗时。
- 旧文件备份、差异、修改副本、精确命令和日志见 `evidence/bot-lifecycle/`。回滚只在另一个副本上测试，修改后的交付文件保留。

## 产品契约

可复用身份、会话关联、持久化、重命名、归档应由产品服务完成；模型负责理解需求与命名/职责，不需要开发源码。简单身份创建以数秒内完成为体验目标，模型响应仍需单独测量。

当前工具保存的是身份与职责，不是一个包含外部账号开通、技能安装、权限授权和实际成员启动的完整 provisioning 管线。若后续增加成员编排，应独立设计 initializing/ready/failed 状态、幂等请求和可恢复阶段，不能把 active 字段当成所有依赖已就绪的证明。
