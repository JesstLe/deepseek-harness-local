# 项目协作规范

本文件适用于本仓库。开工先阅读相关模块文档及 [协作与交接说明](docs/AGENT_COLLABORATION.md)。

## Git 与协作

- 开工先读相关模块文档，检查工作树并执行 `git fetch origin main`，记录基线 SHA。每个任务使用独立 `codex/<任务名>` 分支/worktree，同文件并行修改先明确负责人。
- 保留共享 checkout 的分支及他人未提交内容；不擅自切分支、reset、clean、stash、覆盖目录或强推 main。只 `git add` 本任务明确路径，不提交环境文件、凭据或密钥。
- **分支是短命缓冲区：完成→普通 merge 合入 main→推送→删除已合并的本任务分支和 worktree，当日闭环。** 清理前核对已合入、工作树干净且无运行任务；只处理本任务资源。生产相关修复不隔夜滞留，小改动以小时计。
- 合并前再次刷新 origin/main，先整合最新主线、解决冲突并集中验证；普通 push 被拒绝时重新整合，不强推。超一天的任务每天整合一次主线；每完成 3 个功能模块也执行一次同步，记录同步前后 SHA 与计数，文档修改不计功能迭代。
- 分支自首提交起超过 48 小时未合并时，在交接文档标红说明原因。
- 发布只从 main 构建固定版本。修复是否已整合以 main 为准，是否已上线以实际运行版本及验收证据为准；Git 合并和推送不等于服务器发布。
- 项目保持 Git 管理并同步 GitHub；缺少远端仓库时建立对应仓库后推送，保留现有历史和配置。

## 集中测试与开发记录

- 尽量完成一个完整模块或业务切片后集中测试，不因每个零碎修改反复跑全量构建。选择覆盖受影响模块的类型、单元、集成和必要端到端验证，发现具体问题后再做定向复测。
- 计费、权限、任务恢复、数据迁移等关键链路覆盖成功、失败、重试及并发边界；效率优先不以省略关键验收为代价。
- 功能验收覆盖提交→持久化/排队→供应商→处理→存储→作品/父子回执→账务→用户可见结果。上游 200、脚本 exit 0、局部测试、构建或合并分别说明证据层级，不混写为线上完成。
- 每推进一个模块，同步更新对应模块文档或 `docs/changes/` 记录，写明调研结论、实现内容、已验证结果、未完成项及下一步，不只依赖会话上下文。重构记录同时说明职责、依赖与迁移状态。
- 纯规则/文档修改执行内容、引用和差异核验，不触发业务发布，不增加功能迭代或成功发布计数。

模块交接记录至少包含：

```text
模块与职责：
公共接口、依赖方向、数据/状态/事务归属：
本次实现与迁移状态：
验证命令、结果及证据层级：
未完成项与下一步：
```
